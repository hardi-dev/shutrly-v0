# Coding Rules

Version: 1.0 · Adopted: 2026-09-25

## General
- Explicit, readable code; small focused units.
- No premature abstractions or unrelated refactors (C-010).
- No dead code, commented-out blocks, or unexplained TODOs; a TODO must reference a feature/BR ID.

## Structure
- Follow the layers in [architecture/overview.md](architecture/overview.md): `app/` → `modules/` → `domain/`; infrastructure behind interfaces.
- `domain/` has zero imports from Next.js, Drizzle, Better Auth, or Google libraries.
- Route handlers and server actions are thin: parse → call module use case → map result.

## Naming
- Use glossary terms ([domain/glossary.md](domain/glossary.md)): `Workspace`, `Project`, `SelectionGroup`, `ProjectAddOn`, not synonyms.
- Files: `kebab-case.ts`; React components `PascalCase` exports in `kebab-case.tsx` files.
- DB: `snake_case` tables/columns (singular table names, e.g. `project_item`); TypeScript: `camelCase`.
- Use cases named as verbs: `createProjectFromService`, `submitSelectionGroup`, `approveAddOn`.
- Enum values `UPPER_SNAKE_CASE`, matching the business rules.

## Types
- TypeScript `strict`; no `any`, no non-null `!` without a comment explaining the guarantee.
- Branded ID types (`WorkspaceId`, `ProjectId`, `AuthUserId`) so IDs cannot be mixed.
- Discriminated unions for package values (`{type:'NUMBER', value}` | `{type:'RANGE', min, max}`) and statuses.
- Money uses a decimal type, never JS `number` arithmetic (ADR-007).

## Validation
- Zod schemas at every trust boundary: form input, server actions, route handlers, JSONB reads/writes, Drive API responses.
- Client validation is UX only; the server re-validates everything (C-004).
- Forms use React Hook Form with `zodResolver`. Each form's Zod schema lives in its module (`modules/<context>/schemas.ts`) and is imported by both the form and the server action — never duplicated.
- React Aria inputs bind through `Controller` inside the `components/ui` wrappers; server-action field errors are applied with `setError`, domain errors shown as form-level messages.

## Data Access
- All DB access goes through `modules/*` repositories/use cases; never from components.
- Every owner query takes a verified `WorkspaceContext` and filters by `workspaceId` (C-101). A repository function without workspace scope must be named `*Unscoped` and justified (e.g. client-token resolution).
- Multi-row invariants run in a single transaction; use `SELECT … FOR UPDATE` on the aggregate row (selection group, invoice) where concurrent writes are possible.
- Select only needed columns for client-facing responses; never return `passwordHash`, tokens of other projects, source URLs, or API keys.
- Migrations are generated by Drizzle, reviewed, and committed; never edit an applied migration.
- DB connections come only from `infrastructure/db`: one Neon `Pool` per request, closed via `ctx.waitUntil(pool.end())`; never a module-level pool (ADR-009).

## Errors and Logging
- Expected failures are typed domain errors (`class SelectionLimitExceededError extends DomainError`) carrying a stable `code`; map to user messages at the edge.
- Never swallow unexpected errors; log with request ID, workspace ID, project ID.
- Redaction: never log passwords, tokens, cookies, WhatsApp URLs, Drive URLs, API keys, client phone/email (C-103).

## UI / Components
- Business logic stays out of components.
- Keep `"use client"` boundaries as small as practical; default to server components.
- Pixel/visual truth is the approved Pencil design referenced in the feature's `design.md`.
- Interactive primitives come from `src/components/ui/*` (React Aria Components + Tailwind); features do not import `react-aria-components` directly or hand-roll dialogs, menus, selects, or grids (ADR-010).
- Style states through React Aria `data-*` attributes and theme tokens; no hard-coded brand colors (workspace branding overrides tokens).
- User-facing copy follows the workspace language; MVP UI language: Indonesian with English fallback. **SPEC GAP:** confirm UI language(s) during first design feature.

## UI States
Cover idle, loading, empty, success, validation error, domain/server error, retry, and disabled states where applicable (C-007).

## Security
- No hard-coded secrets; read from environment/secret bindings.
- Public endpoints (`/g/*`, `/i/*`, media proxy): rate-limited, `Cache-Control: private, no-store`, token + status + expiry checked on every request.
- Hash gallery passwords with a slow password hash (Argon2id or scrypt, whichever runs on the selected runtime).
- Generate tokens with a CSPRNG, ≥128 bits of entropy, URL-safe encoding.

## Testing
- Unit-test domain logic; name/describe tests with the `BR-*`/`AC-*` IDs they cover.
- Integration-test use cases against real Postgres, including cross-workspace isolation and concurrency (selection submit, payment record).
- The integration database is shared (ADR-009): every test seeds its own workspace/user with unique IDs, asserts only on its own data, and never truncates or deletes other data. Never point tests at production.
- E2E-test critical journeys J-01, J-04, J-06, J-07.
- Test behavior, not implementation details.

## Git
- Small commits per iteration; conventional commit prefixes (`feat:`, `fix:`, `docs:`, `chore:`, `test:`).
- Docs change in the same commit as the behavior they describe (C-011).

## Quality Gate
An iteration is complete only when:
- typecheck, lint, and relevant tests pass; build passes
- migrations reviewed
- constitution and coding-rules compliance checked
- acceptance criteria verified and mapped to tests
- deviations / `SPEC GAP`s reported
